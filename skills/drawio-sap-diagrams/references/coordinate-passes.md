# Step 4 詳細: 3 パス座標構成

`SKILL.md` の Step 4 で参照する **draw.io XML 生成の 3 パス手順** の詳細。`SKILL.md` 本体は概要だけ持ち、ここでメカニクスを完結させる。

## 全体像

```
4a  要素棚卸し（座標を書かない）
    ↓
4b-1 論理座標（主軸変数 + 相対式で位置を定義）
    ↓
4b-2 物理座標（変数を確定 → 式を評価 → XML 出力）
```

**なぜ 3 パスに分けるか**: 「セル構造」「論理座標（相対式）」「物理座標（px 値）」を一度に書くと、後の修正で連鎖的なやり直しが発生する。

- **4a（棚卸し）**: 構造ミスを早期発見する。座標を一切書かないことでレイアウト議論に集中できる
- **4b-1（論理座標）**: 主軸変数 + 相対式で位置関係を定義する。ラベル長変更・要素移動・主軸ずらしは「式の変更」だけで済む
- **4b-2（物理座標）**: 4b-1 の式を評価して px 値を確定する。修正時は 4b-1 に戻って式を更新する

実例: `Subaccount.h = (最下段要素のラベル底辺) - Subaccount.y + MARGIN` と式で定義しておけば、「branches を上→下に移動」のような修正でも空白問題は構造的に発生しない（過去の失敗ケースは修正時に式を立て直さず px を直接 Edit したことで起きた）。

---

## Step 4 事前準備（スタイル未定義の洗い出し）

3 パスに入る前に、以下を一度だけ済ませる。

1. **必要要素の棚卸し**: その図で使うサービスアイコン名・ボックス種別・新規のレイアウトパターンを列挙する
2. **references に存在するか確認**: `references/elements.md` の SAPIcon 表、`references/layout.md` の標準サイズ表、`references/guidelines.md` を突き合わせる
3. **不明点を一括でユーザーに確認**: 不明な SAPIcon 名や未定義パターンを **全部まとめて** 聞く（遭遇するたびに聞くと会話が細切れになる）

---

## Step 4a: 要素棚卸しパス（座標を書かない）

XML を書き始める前に、**座標なし** で全セルをテキストで棚卸しする。サイズは `references/layout.md` の標準値を引用するだけ（この時点で計算はしない）。

棚卸し項目（箇条書きで出力）:

- **コンテナ・ボックス**: ID / 種別（BTP, Subaccount, サービスボックス等）/ サイズ（標準値）/ 親コンテナ
- **アイコン・ラベル**: ID / 種別（SAPIcon 名 / Generic Icon プレースホルダ）/ 親コンテナ / ラベル文字列
- **エッジ**: ID / source → target / スタイル種別（直線 / orthogonal / trust / authenticate 等）

この時点でユーザーに共有してもよい。構造ミス（親子関係の誤り、エッジの欠落、ボックス種別の選択ミス）はここで気付けば修正コストが小さい。

---

## Step 4b-1: 論理座標パス（変数と相対式で定義する）

XML を書く前に、座標を **「主軸変数」+「相対式」** の形でテキスト化する。直接 px 値を書かない。

定義する主軸変数（典型例）:

- `main_axis_Y` — 横並び主フローの中心 Y
- `main_axis_X` — 縦並びの中心 X（縦フローの場合）
- `H_GAP` — 要素間の水平ギャップ（ラベル端からの clearance）
- `V_GAP` — 要素間の垂直ギャップ
- `MARGIN_INNER` — コンテナ内側の余白
- `BTP_TOP` / `SUB_TOP` 等 — 各コンテナの起点座標

各要素は主軸 / 他要素を参照した式で書く:

```
BWZ.center_Y = main_axis_Y
BWZ.x        = SUB_LEFT + 35
Dest.x       = BWZ.right + H_GAP + dest_label.half_width - icon_half
CF.x         = Dest.right + H_GAP + dest_label.half_width
Subaccount.h = (HTML5.bottom + label_height) - Subaccount.y + MARGIN_INNER
BTP.h        = (CIS.bottom + cis_label_height + 20) - BTP.y
```

**ねらい**: 後で「主軸を上にずらす」「ギャップを広げる」「ラベル幅が変わる」といった修正が来たら、変数 1 つを変えれば全体が連動する。芋づる式の手計算を排除する。

---

## Step 4b-2: 物理座標パス（変数を確定して XML を書き出す）

4b-1 の主軸変数に具体的な px 値を割り当て、式を評価して XML に書き出す。

計算順序:

1. **主軸変数の確定**: `main_axis_Y` / `H_GAP` / コンテナ起点などを決める
2. **相対式の評価**: 4b-1 の式に値を入れて各要素の絶対座標を算出
3. **エッジの接続点**: 直線で結ぶエッジは両端のセル中心座標が一致するよう揃える（`references/layout.md` §4）
4. **XML 出力**: `<mxCell>` を書き出す

修正が必要な場合（要素を増やす・ラベル幅が変わる・主軸をずらす）は **4b-1 に戻って式を更新** し、4b-2 を再実行する。XML を直接 Edit する誘惑を抑える。

---

## 座標の粒度

Claude が XML を書く際、座標は粗く決めて良い。**最終的な位置微調整は人間が draw.io 上で行う**。Claude が厳密に合わせるべきなのは以下だけ:

- **直線矢印で結ぶ要素の中心座標**（中心が 1 px でもずれると orthogonal に折れ曲がる、`references/layout.md` §4 参照）
- **コンテナの内外関係**（BTP の中 / Subaccount の中 / ボックスの中、の所属）

それ以外（コンテナの幅・高さ、余白、矢印のベンド点など）はおおよそで良い。ピクセル単位の計算に時間をかけるより、粗い XML を早く出してユーザーのフィードバックを受ける方が速い。

---

## スタイルの source of truth

- **`references/guidelines.md` = SAP 公式ガイドラインの日本語要約 = source of truth**
- **`references/layout.md` / `references/elements.md` = guidelines を draw.io XML として具体化した実装層**
- 実装層と公式が食い違う場合は、原則として実装層を公式に合わせて修正する。Claude は食い違いを見つけても勝手に直さず、**ユーザーに報告してから対応** する（過去の iteration で意図的にずらしている可能性があるため）。
